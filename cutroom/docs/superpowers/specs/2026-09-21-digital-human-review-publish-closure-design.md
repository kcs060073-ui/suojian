# 数字人精剪、审片返工与发布闭环设计

日期：2026-09-21

状态：产品设计已确认，待书面规格复核

## 1. 目标

在现有 CUTROOM 工作台和数字人生产链上，完成从包装确认到正式发布包的后半程闭环：

```text
包装确认
  → 精剪渲染
  → 自动 QA
  → 完整审片
  → 分类返工
  → 新候选版本
  → 再次 QA / 审片
  → 发布包
```

本阶段不以“能够生成视频”作为完成标准，而以候选版本、QA、完整审片、分类返工和发布包之间存在可靠、可恢复、可追溯的门禁关系为准。

## 2. 继承关系与当前缺口

本设计继承：

- `2026-09-05-colleague-video-workbench-design.md` 定义的十二步主链、四道人工作业门禁和版本链。
- 已完成的粗剪真实媒体闭环和包装预览闭环。
- 现有 `media_catalog` 中的渲染、QA、审片决定和发布包能力。
- 已确认的 V4 工作台视觉语言、导航结构和阶段式操作心智。

当前工作台已经能够展示候选视频、记录观看进度、批准候选版本并生成发布包，但仍有以下缺口：

- 精剪、QA 和完整审片混合在同一区域，阶段责任和阻断原因不清晰。
- 驳回能力只有单一的“记录画面返工”，不能按文案、素材、节奏、字幕、声音、包装和技术问题分流。
- 缺少候选版本历史以及新旧版本的 QA、观看和批准状态隔离。
- 缺少返工后下游门禁的精确失效和局部重跑规则。
- 发布包没有充分呈现其绑定候选版本以及返工后的过期状态。
- 尚未用一条真实数字人任务验证“驳回—返工—新候选—再审片—发布”的完整链路。

## 3. 方案选择

采用“数字人纵向闭环”方案：保留现有工作台骨架和后端模块，沿数字人路线补齐候选版本、分类返工、局部门禁失效、再审片和发布包绑定。

没有采用以下方案：

1. 只改界面：能改善可读性，但无法解决版本串用、门禁残留和返工追溯问题。
2. 先重写统一任务状态机：长期一致性更强，但本阶段改动面过大，会推迟真实后半程闭环。

本方案要求后端先形成可靠领域规则，界面只呈现和调用这些规则，不在浏览器中自行推算门禁状态。

## 4. 产品范围

本阶段包括：

- 候选版本历史、来源关系和状态展示。
- QA 阻断项、警告项和通过项的分级展示。
- 与候选版本绑定的真实完整审片进度。
- 分类返工、影响范围预览、用户确认和局部回退。
- 新候选版本生成以及旧版本只读保留。
- 发布包与已批准候选版本的强绑定和过期标记。
- 自动化测试与一条真实数字人任务验收。

本阶段不包括：

- 信息流广告路线的完整纵向改造。
- 园区样片路线验收。
- 自动登录或发布到外部内容平台。
- 任意多轨时间线编辑器。
- 整套工作流状态机重写。
- 默认自动调用付费 AI 或外部生成服务。

## 5. 总体架构

本阶段继续复用现有渲染、QA、审片和发布模块，在其上增加候选版本与返工编排层：

```text
工作台界面
  ├─ 候选版本与 QA 展示
  ├─ 完整审片进度与决定
  ├─ 分类返工确认
  └─ 发布包状态
          │
工作台动作 / API
          │
候选与返工编排层
  ├─ 版本创建与输入摘要
  ├─ 分类到回退阶段映射
  ├─ 下游门禁失效
  ├─ 幂等与费用确认
  └─ 发布包绑定与过期
          │
现有能力
  ├─ 精剪渲染
  ├─ 自动 QA
  ├─ 审片记录与决定
  └─ 发布包生成
```

编排层必须是门禁状态的唯一解释者。界面不得根据按钮点击历史推断“已通过”，也不得把一个候选版本的观看进度或批准结果复制给另一个版本。

## 6. 领域模型

### 6.1 CandidateVersion

每次视频内容或渲染输入发生变化时创建独立候选版本，至少记录：

- 任务 ID。
- 稳定的候选版本 ID 和任务内递增版本号，如 `candidate-v1`。
- 来源候选版本 ID，可为空。
- 触发本版本的返工单 ID，可为空。
- 输入摘要，包括脚本、素材、粗剪、画面锁定和包装配置的稳定指纹。
- 视频产物位置、校验值、时长和生成时间。
- 渲染、QA、审片和发布状态。
- 创建原因和修改摘要。

候选版本状态为：

```text
待渲染 → 渲染中 → QA 中 → QA 阻断 / 待审片
→ 审片中 → 已驳回 / 已批准 → 已发布
```

失败是各执行状态上的可恢复结果，不创建一个可以被误认为有效候选的半成品版本。

### 6.2 QAReportRevision

QA 报告必须绑定候选视频校验值，并记录：

- 报告修订号。
- 执行时间和检测器版本。
- 阻断项、警告项和通过项。
- 每个问题的时间范围、依据、推荐返工分类和建议回退阶段。

视频文件未变化时可重新运行 QA 并生成新的报告修订号，不需要增加候选版本号。视频内容或渲染输入发生变化时必须创建新候选版本。

### 6.3 WatchSession

观看记录绑定用户、任务和候选版本，至少记录已真实播放区间、有效观看比例和最后更新时间。拖动到未观看区域不计入完整观看。

不同候选版本的观看记录完全隔离。旧候选版本达到 100% 不得解锁新候选版本的批准按钮。

### 6.4 ReviewDecision

批准或驳回决定必须绑定明确的候选版本和当时的 QA 报告修订号。批准要求：

- 当前候选视频文件仍与 QA 报告校验值一致。
- 当前 QA 无阻断项。
- 当前候选版本观看进度为 100%。
- 当前上游输入摘要未失效。

### 6.5 ReworkRequest

返工单至少记录：

- 来源候选版本。
- 问题分类、说明和视频时间点。
- 可选的 QA 问题引用或截图引用。
- 系统计算的目标回退阶段。
- 将保留和失效的阶段结果。
- 建议重跑范围。
- 是否涉及外部生成或费用。
- 用户确认状态、执行状态和产生的新候选版本。

返工单状态为：

```text
草稿 → 待确认 → 执行中 → 已生成新版本 / 已取消
                         ↘ 执行失败
```

### 6.6 PublishPackage

发布包必须绑定一个明确的已批准候选版本和对应校验值，至少包含成片、封面、标题、描述、字幕或附件、QA 报告以及审片批准记录。

候选版本发生内容返工后，旧发布包标记为“已过期”，保留查看和下载能力，但不再作为任务当前正式发布包。

## 7. 版本与门禁规则

1. 旧候选版本保持只读，所有历史报告、观看、决定和发布包均保留。
2. 新候选版本不得继承旧版本的 QA、观看进度、批准结果或发布状态。
3. 相同输入摘要和相同动作幂等键的重复请求必须复用已有结果，不能重复渲染、创建版本或计费。
4. 上游输入发生变化后，依赖该输入的下游门禁失效，但历史记录不删除。
5. 发布包只能引用确定版本，不得绑定会随时间变化的“当前最新版本”。
6. 只有内容和输入均未变化的 QA 重跑可以在同一候选版本下增加报告修订号。
7. 候选视频校验值、QA 报告校验值和批准时校验值不一致时，批准门禁必须关闭。

## 8. 分类返工与局部回退

| 问题分类 | 回退阶段 | 保留内容 | 必须重新执行 |
|---|---|---|---|
| 文案 | 文案确认 | 原素材和历史版本 | 文案确认、同步、分镜、粗剪、锁画、包装、精剪、QA、审片 |
| 素材 | 分镜或粗剪 | 已确认文案 | 素材匹配、粗剪、锁画、包装、精剪、QA、审片 |
| 节奏 | 粗剪 | 文案和素材选择 | 粗剪、锁画、包装、精剪、QA、审片 |
| 字幕 | 包装 | 画面锁定版本 | 字幕或包装、精剪、QA、审片 |
| 声音 | 包装或精剪 | 画面锁定版本 | 音频处理、精剪、QA、审片 |
| 包装 | 包装 | 文案、粗剪和画面锁定 | 包装、精剪、QA、审片 |
| 技术问题 | 精剪或 QA | 上游创作结果 | 按报告重渲染或重新 QA |

系统计算回退范围后，必须在执行前向用户展示：

- 返回哪个阶段。
- 哪些结果继续有效。
- 哪些结果将失效。
- 将重新运行哪些动作。
- 是否可能调用付费或外部服务。

保存返工单不执行回退；只有用户明确点击“确认返工并回到对应阶段”才开始执行。若需要付费生成，仍需独立确认，不得把“驳回”视为付费授权。

## 9. 端到端数据流

```text
包装确认
  → 计算精剪输入摘要
  → 幂等创建渲染运行
  → 成功后落库候选版本和视频校验值
  → 运行 QA 并绑定校验值
  → 无阻断项后开放完整审片
  → 持久化真实观看区间
  → 用户批准或分类驳回
      ├─ 批准：绑定候选版本与 QA 修订号
      │        → 生成绑定版本的发布包
      └─ 驳回：生成返工单
               → 展示影响范围与费用
               → 用户确认
               → 失效目标阶段之后的当前门禁
               → 局部修改与重跑
               → 创建新候选版本
               → 重新 QA 和完整审片
```

返工失败时，来源候选版本继续可查看。系统不得因为新版本生成失败而破坏上一个候选版本或把任务错误标记为已通过。

## 10. 工作台界面

本阶段保留现有全局导航、任务上下文栏、工作区骨架、主要视觉语言以及前半程阶段页面，仅定向改造后半程工作区。

### 10.1 精剪候选版本区

展示当前候选版本、状态、生成时间、来源版本、修改摘要和输入是否仍有效。提供历史版本切换入口。

切换旧版本后必须显示明显的“历史版本”标识，并禁用审批、返工执行和正式发布等会改变当前任务状态的操作。查看和下载历史产物仍然允许。

### 10.2 自动 QA 区

QA 结果分为阻断项、警告项和已通过项：

- 阻断项禁止批准。
- 警告项允许继续审片，但批准时再次提示。
- 已通过项默认折叠。

每个问题展示类型、时间点或范围、检测依据、推荐返工分类和建议回退阶段，并提供“跳转到对应时间”。QA 失败时保留视频，提供“重试 QA”和“按问题创建返工单”。

### 10.3 完整审片区

播放器与候选版本的真实观看区间绑定：

- 拖动不计入未播放区间。
- 页面刷新后恢复当前版本记录。
- 切换候选版本后独立计算。
- 100% 观看且 QA 无阻断项后才能批准。
- 驳回不要求观看完成，发现问题即可记录。

### 10.4 分类返工对话框

返工对话框依次收集问题分类、说明、当前播放时间点、可选证据，并展示系统计算的回退阶段、保留结果、失效结果、重跑动作和成本提示。

提供两个不同语义的主操作：

- “保存返工单”：只记录问题。
- “确认返工并回到对应阶段”：执行回退和后续编排。

### 10.5 发布区

发布区明确显示绑定候选版本，并列出成片及校验值、封面、标题、描述、字幕和附件、QA 报告、批准记录、生成时间与状态。

返工后旧发布包显示“已过期”，不得继续显示为当前正式发布包。

### 10.6 操作反馈

所有长操作使用一致状态：

```text
待执行 → 执行中 → 成功
               ↘ 失败：原因 + 可恢复操作
```

提交后立即禁用重复动作。失败提示必须包含下一步，例如重试 QA、继续查看旧版本、修正输入或返回对应阶段，不能只显示“操作失败”。

## 11. 接口责任边界

工作台动作层至少需要支持以下业务动作，具体 URL 和存储表名在实施计划中结合现有代码确定：

- 查询任务候选版本列表与当前版本。
- 查询候选版本的 QA 修订、观看记录、审片决定和发布包。
- 写入候选版本的真实观看区间。
- 重试候选版本 QA。
- 创建和更新返工单。
- 预览返工影响范围。
- 用户确认并执行返工。
- 批准或驳回明确候选版本。
- 为明确候选版本生成或重试发布包。

所有改变状态的动作必须接受幂等键，并在服务端重新验证候选版本、校验值和门禁条件，不能信任前端提交的“已观看”或“QA 已通过”布尔值。

## 12. 异常恢复

- 精剪失败：保留旧候选版本；不产生可用的半成品候选；支持从失败动作重试。
- QA 失败：候选视频仍可播放但不能批准；支持单独重试 QA。
- 观看记录写入失败：明确显示未保存并重试；不得虚假展示 100%。
- 返工失败：返工单记录失败原因；来源候选和有效历史门禁不被破坏。
- 发布包失败：候选批准状态保持有效；支持单独重试发布包。
- 页面刷新或服务重启：从持久化状态恢复，不依赖浏览器内存。
- 重复请求：依靠幂等键和输入摘要防止重复产物、版本和费用。

## 13. 测试策略

### 13.1 后端自动化测试

- 分类与回退阶段映射。
- 候选版本递增、来源关系和输入摘要。
- 新旧版本的 QA、观看和批准隔离。
- 下游门禁失效与历史保留。
- QA 修订与候选版本变化的边界。
- 重复请求幂等。
- 渲染、QA、返工和发布失败恢复。
- 发布包绑定和过期处理。

### 13.2 前端自动化测试

- 候选版本切换和历史版本只读状态。
- QA 阻断、警告及跳转时间点。
- 分类返工的保存、预览和确认流程。
- 观看进度与候选版本隔离。
- 批准、返工和发布按钮门禁。
- 长操作加载、防重复提交、失败和重试。
- 旧发布包过期提示。

### 13.3 回归测试

必须运行项目现有 Python、TypeScript 和 Web 测试，并验证本阶段没有破坏已经完成的粗剪真实媒体闭环和包装预览闭环。

## 14. 真实任务验收

使用隔离数据库完成一条真实数字人任务：

```text
包装确认
→ 精剪渲染
→ QA
→ 人工完整观看
→ 分类驳回
→ 局部返工
→ candidate-v2
→ 再次 QA
→ 人工完整观看
→ 批准
→ 生成发布包
```

验收证据必须证明：

- `candidate-v1` 的视频、QA、观看、决定和返工历史完整保留。
- `candidate-v2` 未继承旧版本观看进度或批准结果。
- 分类返工只回退到必要阶段。
- QA 阻断项确实阻止批准。
- 两次完整观看均由人工完成，测试代码不得伪造 100%。
- 发布包绑定 `candidate-v2`，产物清单和校验值完整。
- Python、TypeScript 和 Web 全量测试通过。
- 粗剪和包装既有验收路径仍然通过。

真实精剪或外部生成可能产生费用时，自动化验收只执行本地可控部分；付费步骤由用户明确确认后运行。

## 15. 完成定义

同时满足以下条件，本阶段才可视为完成：

1. 候选版本、QA、审片、返工和发布包形成持久化证据链。
2. 新旧候选版本的门禁完全隔离。
3. 七类问题均能映射到正确回退范围，并在执行前向用户解释影响。
4. 返工产生新候选版本，旧版本与旧发布包不被覆盖。
5. 工作台后半程状态清晰，错误均有可恢复操作。
6. 自动化测试和真实数字人任务验收均通过。
7. 没有未经确认调用付费生成或外部发布服务。
